## Current result

The approved day 1–30 mission is **not implemented**. Existing systems supply real mechanics, but cannot deliver the approved sequence by changing UI text or rescue constants alone.

| Required beat | Existing reusable implementation | Remaining domain work and meaningful player decision |
|---|---|---|
| Days 1–2: repair, meal, secured sleep | Repair/EVA interactions; actual ration and drink debits; ordinary sleep <=8.5 h | Activate needs, meal and sleep before contact. Currently `SurvivalExtension.IsActive` requires contact plus `GamePhase.Survival`; `Begin()` runs only after the first reply. Separate survival activation from contact/recovery activation, with one transition from continuous provisioning to portion accounting. First meal must become legitimately available; the current portion gate requires six hours of unmet need. Physical pouch and restraint sequences remain separate presentation/body work. |
| Day 5: consequences and reserves | `FieldModifications.TrySalvagePayload()` irreversibly abandons science, credits parts and removes its electrical load; absorber construction/install use actual parts and battery | Present a real preserve-science versus salvage choice with forecast consequences. Gate continuation on an explicit decision; observe the existing salvage interaction, do not duplicate its debit. Ensure a science payload is actually aboard, or author a valid alternative. Generic equipment shutdown does not currently exist. |
| Day 9: exterior repair and contact | Suit preparation, airlock, EVA exit/return, antenna/power repair, cockpit transmission; `ICommunicationSystem.TryTransmit()` enforces prerequisites and causal reply delay | Schedule the exterior task/contact chapter without resetting completed repairs. Keep unresolved antenna work until this beat, or author an additional exterior task if already repaired. Require safe return before routine. The first reply starts survival/recovery today; decouple that behavior from day-1 survival. |
| Day 14: first rescue fails | Single initial distress/reply exchange; journal; current recovery stages | Add a second, timestamped rescue-failure dispatch and an acknowledgement/decision gate. Current `RecoveryStage.Delayed` means a missed beacon (+3 days), not failed rescue. Set revised arrival to mission day 30 for an already-in-transit craft; record and display actual remaining reserves. |
| Days 20–30: final choice, beacon, rendezvous | Actual beacon cost (0.4 kWh), 8 h request window, recovery/loss outcome and ending sequence | Add a late power/supply tradeoff with a measurable cost: e.g. stop the growing module to preserve beacon energy, forfeiting its pending harvest. This shutdown command does not exist. Derive whether it matters from the ledger/forecast; no fake emergency. Day-30 recovery must require the chosen beacon/survival prerequisites; replace the current automatic +12 days after contact / missed-beacon +3 days behavior for this approved mode. |

Day numbers are one-based: day N begins at `(N - 1) * 86400` simulated seconds (`MissionCalendar`). Use that epoch for chapter thresholds, not contact-relative offsets or a second counter. A target day means a boundary inside that day, not permission to erase elapsed time if a player reaches prerequisites late; overdue dispatches stay causal and missed windows need an explicit outcome.

## Critical routine gap

`MissionSession.AdvanceSimulation()` already advances the real ledger, calendar, EVA, modifications, needs, growth and communications. Its boundary splitting stops mission loss at the correct time. It is **not** a safe public routine command: it keeps consuming the requested budget after nonfatal milestones, defers event delivery until the whole advance completes, and stops consulting boundaries after 32 splits. The finite-scale early-exit path is used by real-time advance, not this public jump. A UI event listener cannot interrupt an already committed multi-day jump.

Awake survival currently spends food/water only through portion commands; resting uses continuous BVAD rates and pauses unmet needs (`MissionDirector`, lines 677–684). A raw three-day awake jump therefore reaches thirst/hunger loss instead of representing ordinary meals. Simply adding continuous food/water to the jump would double-charge portions or erase unmet need unless Core explicitly owns the routine mode and its accounting.

Recommended implementation: a bounded, resumable Core routine state machine, driven by the existing session clock. Its schedule uses real meal/drink commands, ordinary rests <=8.5 h and their current accounting; split exactly at meal, sleep, hazard, crop, dispatch and chapter boundaries. Each step must inspect authoritative stop conditions synchronously before accepting the remaining budget. Preserve original clock scale, needs, crop age, pending communications and actual elapsed time. Never allow the 32-split fallback to bypass a required routine boundary; yield with unspent budget instead. Routine entry must reject EVA/open airlock, unresolved repairs, active choices, terminal state and pause. Danger wins a simultaneous meal, harvest or rescue. A crop-ready/failed event stops for player attention; do not auto-harvest unseen.

## Smallest coordinated contract proposal (not approved or implemented)

Keep `ISurvivalExtension`, `ISurvivalRecovery`, `IEvaStatus`, `IFieldModifications`, `IResourceSystem`, `ISimulationClock` and existing interaction IDs. No new UI-owned simulation, generic resource-mutating command or unrestricted “skip to day” API is needed.

Add `IMissionChapterFlow` under Contracts, implemented by Core and exposed by `MissionSession`/composition:

- `ChapterSnapshot Snapshot { get; }`: typed `ChapterId`, `RoutineState`, nullable next-boundary simulation time, routine start/actual elapsed seconds, `RoutineStopReason`, and current decision ID. Calendar/day remains the existing clock mapping; snapshot does not own a second calendar. Include a monotonically changing revision for one-time presentation cues.
- `CommandResult CheckContinueRoutine()` and `TryContinueRoutine()`: Core chooses the next eligible beat and rechecks prerequisites. Accepting the command starts bounded advancement, not an atomic multi-day jump.
- `CommandResult TryCancelRoutine()`: cancel at current committed time, restore control/clock rate, no rewind/refund. Pause suspends routine without advancing; restart/disposal cancels it and removes callbacks.
- `CommandResult CheckChoose(ChapterChoice choice)` and `TryChoose(ChapterChoice choice)`: a finite authored set, initially `PreserveScience`, `StopGrowForBeacon`, `KeepGrowRunning`, `AcknowledgeRescueFailure`. Salvage itself continues through the existing interaction, whose successful domain state resolves that branch. Reject choices outside the current decision and duplicates; `StopGrowForBeacon` invokes a new Core grow-stop operation, removes load/irrigation and forfeits the crop without crediting food or refunding costs.
- `event Action Changed`: publish committed state changes. `RoutineStopReason` needs at least `ReachedChapter`, `PlayerCancelled`, `Danger`, `ResourceShortage`, `CropReady`, `CropFailed`, `DispatchReceived`, `DecisionRequired`, `PrerequisiteMissing`, `MissionEnded`; existing `RestStopReason` continues to mean an individual sleep, not routine.

Extend recovery's readable state with an explicit `FirstRescueFailed` milestone (or a separate typed recovery-plan status), and a late `AwaitingBeacon`/committed-arrival distinction. Reuse `TryPowerBeacon()` and arrival timestamps. New code must not interpret the legacy `Delayed` enum as first-rescue failure. Update existing switch consumers/journal/report text together.

Add a typed `MissionDispatchReceived` event carrying dispatch ID, sender, transmitted/received simulation timestamps and content ID. Core schedules the day-14 dispatch; receipt cannot precede the relevant one-way delay, or outbound plus processing plus return delay if responding to a player request. Expose the latest received dispatch in the chapter snapshot (or a read-only history) so reconnecting presenters can reconstruct state. Do not force the one-shot `ICommunicationSystem.TryTransmit()` to restart its initial timer. Audio/subtitles consume the event and never advance delivery time.

Meal choreography can call the existing ration command once at the actual consumption moment and animate only on success; repeated animation events must not issue another consume. A sealed ready-to-eat pouch needs no new contract. If an actual rehydration/heating recipe is chosen, Core needs an atomic prepared-meal state/recipe cost including water/energy; presentation cannot charge it independently or manufacture food. This extension is conditional on the chosen prop/recipe, not required for every pouch.
